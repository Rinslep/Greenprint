## Scraper Source Reference

### Factorio Prints / Factorio School — Same Database

**Critical finding:** `factorioprints.com` and `factorio.school` are the **same database**.
factorio.school is the newer frontend for the same Firebase backend. Scraping both sites would
produce pure duplicates. **Scrape one, not both.**

The backend is **Firebase Realtime Database**, which exposes a public REST API — no authentication
required for read access. Any path in the database can be queried by appending `.json` to the URL.

The two relevant Firebase paths are:
- `/blueprintSummaries` — lightweight metadata for all blueprints (title, tags, author, timestamps)
- `/blueprints` — full blueprint data including the encoded string

The Firebase project name visible in the site source is `facorio-blueprints` (note the typo — one
`t`). The REST base URL pattern is:
```
https://facorio-blueprints-default-rtdb.firebaseio.com/blueprintSummaries.json
https://facorio-blueprints-default-rtdb.firebaseio.com/blueprints/{id}.json
```

**This means the Factorio Prints / School scraper is not really a scraper at all — it is a
Firebase REST client.** No HTML parsing, no Playwright, no rate-limit guessing. Fetch
`/blueprintSummaries.json` to get all IDs, then fetch each `/blueprints/{id}.json` individually.

Firebase supports pagination via `orderBy`, `limitToFirst`, and `startAt` query parameters.
Use these rather than fetching the entire summary list at once, which can be large.

Practical approach:
1. Fetch `/blueprintSummaries.json?orderBy="$key"&limitToFirst=1000` to get the first page
2. Use the last returned key as the `startAt` value for the next page
3. For each summary, fetch `/blueprints/{id}.json` for the full blueprint string
4. Store the Firebase key as `source_id` for resumability

**Be polite:** Firebase is a paid service for the site owner. Add a small delay between requests
(0.5–1s) and avoid hammering it. There is no published rate limit but the owner pays per read.

### Factorio Forums

The forums run **phpBB** — standard paginated HTML, no JavaScript rendering required.
BeautifulSoup with `httpx` is sufficient. No API exists.

Relevant subforums for blueprints:
- `viewforum.php?f=8` — Show your Creations (main)
- `viewforum.php?f=194` — Mechanical Throughput Magic (circuit-free belt/inserter designs)
- `viewforum.php?f=193` — Combinator Creations

Pagination pattern: `viewforum.php?f=8&start=25`, `&start=50`, etc. (25 posts per page by default).

Each topic is at `viewtopic.php?t={id}`. Topics can have multiple pages:
`viewtopic.php?t={id}&start=15`.

Blueprint strings appear inline in post bodies, not in structured fields. The extraction regex
must handle:
- Strings split across lines by the forum's text wrapping
- `[code]...[/code]` bbcode blocks (the most common wrapping)
- Inline strings without any wrapping

The forum does not require login to read. Check `robots.txt` before scraping.
Use a 1–2 second delay between requests — the forums are run by Wube (the developers) directly.

## Entry Points

The project needs a flexible CLI that can run the entire pipeline or individual stages.
This matters now because you need to run parts independently during development, and it matters
later because a hosted site needs to trigger analysis on demand.

### Recommended: Typer CLI

Typer integrates naturally with FastAPI (both use the same ecosystem), is clean to write,
and produces good help text automatically. Structure it as a single `cli.py` entry point
with subcommands:

```
python -m greenprint scrape [--source factorioprints|forums|all] [--limit N]
python -m greenprint ingest              # decode + validate + version filter
python -m greenprint analyse [--id ID]   # run full analysis on stored blueprints
python -m greenprint analyse --stage crafting_graph   # run one stage only
python -m greenprint review              # launch review queue interface
python -m greenprint serve               # start the FastAPI server
python -m greenprint pipeline            # run everything end to end
```

The `--stage` flag on `analyse` is the key design decision. Each analysis stage (crafting graph,
ratio, throughput, motif) should be independently re-runnable on already-ingested blueprints.
This lets you:
- Re-run just the motif analysis after fixing a bug without re-scraping
- Run analysis on a single blueprint by ID for debugging
- Trigger individual stages from the web UI later

### How the Web UI Triggers Analysis

When hosting, the web UI will need to trigger pipeline stages via the API. Design for this by
making every CLI stage also callable as a function — the CLI subcommand just calls the same
function the API endpoint calls. Never put logic inside the CLI handler itself.

```python
# analysis/crafting_graph.py
def run(blueprint_id: str | None = None) -> AnalysisResult:
    ...

# cli.py
@app.command()
def analyse(blueprint_id: str | None = None):
    result = analysis.crafting_graph.run(blueprint_id)
    ...

# api/v1/analysis.py
@router.post("/analysis/crafting-graph")
def trigger_crafting_graph(blueprint_id: str | None = None):
    result = analysis.crafting_graph.run(blueprint_id)
    ...
```

This pattern means the web UI, CLI, and any future automation all share exactly the same code
path with no duplication.

### Long-Running Jobs

Scraping 50,000 blueprints and running full analysis takes hours. For the CLI this is fine — it
runs in the foreground with progress output. For the web UI, you will eventually want a task
queue (Celery + Redis, or simpler options like `arq`). Design the analysis functions to be
stateless and idempotent now so that wiring them into a queue later requires no refactoring:
- Each function accepts an ID or range, does its work, writes to the database, returns a result
- Running the same function twice on the same input produces the same output
- No global mutable state

## Logging Strategy

### Use `structlog`

Plain Python `logging` produces unstructured text that is hard to query when something goes wrong
on the 40,000th blueprint. `structlog` produces structured key-value output that can be filtered,
searched, and later shipped to a log aggregator when hosting.

Install: `structlog`, `rich` (for pretty dev console output)

### Two-Mode Configuration

Configure logging differently for development vs production via an environment variable or
config flag:

**Development mode** (`LOG_MODE=dev`):
- Pretty-printed, colourised console output via `structlog` + `rich`
- Log level: `DEBUG`
- Every pipeline stage emits detailed events with full context
- Each blueprint's processing steps are individually logged with blueprint ID, source URL,
  and current stage
- Failures include the full exception traceback and the raw string hash for reproduction

**Production mode** (`LOG_MODE=prod`):
- JSON output, one object per line (suitable for log aggregators)
- Log level: `INFO` (configurable via `LOG_LEVEL` env var)
- Failures still include full context but no pretty formatting

```python
# logging_config.py
import structlog
import logging

def configure_logging(dev_mode: bool = False):
    processors = [
        structlog.contextvars.merge_contextvars,
        structlog.processors.add_log_level,
        structlog.processors.TimeStamper(fmt="iso"),
    ]

    if dev_mode:
        processors.append(structlog.dev.ConsoleRenderer())
    else:
        processors.append(structlog.processors.JSONRenderer())

    structlog.configure(processors=processors)
    logging.basicConfig(level=logging.DEBUG if dev_mode else logging.INFO)
```

### What to Log at Each Stage

**Scraper:**
- `INFO` — starting scrape of source, total items expected
- `DEBUG` — each page fetched, item count on page, next cursor/offset
- `INFO` — each blueprint string extracted with source URL and raw hash
- `WARNING` — rate limit hit, backing off
- `INFO` — scrape complete, total fetched, total new, total duplicate

**Decoder:**
- `DEBUG` — decoding blueprint {hash} from {source_url}
- `DEBUG` — blueprint book dissolved into {n} children
- `WARNING` — decode failed at stage {stage}: {reason} for hash {hash}
- Failures are logged then recorded in the database — never silently swallowed

**Validator:**
- `DEBUG` — validating {hash}
- `WARNING` — schema violation: {field} — {detail}
- `WARNING` — semantic violation: {check} — {detail}

**Version filter:**
- `DEBUG` — version {major}.{minor}.{patch} accepted/rejected for {hash}
- `INFO` — modded blueprint rejected: unknown entity {name} in {hash}

**Analysis stages:**
- `INFO` — starting {stage} analysis for {n} blueprints
- `DEBUG` — blueprint {id}: {stage} complete — {summary of result}
- `WARNING` — blueprint {id}: cycle detected in crafting graph
- `WARNING` — blueprint {id}: recipe inference required for {n} machines
- `INFO` — {stage} complete: {n} succeeded, {n} failed, {n} flagged

### Structured Context Binding

Use `structlog.contextvars.bind_contextvars` to attach the current blueprint ID to all log
events within a processing block, so every log line for a given blueprint automatically
includes its ID without manually passing it to every function:

```python
import structlog.contextvars as ctx

def process_blueprint(blueprint_id: str):
    ctx.bind_contextvars(blueprint_id=blueprint_id)
    # every log call inside here automatically includes blueprint_id=...
    decode(...)
    validate(...)
    ctx.clear_contextvars()
```

### Progress Display During Development

For long-running operations (scraping, batch analysis), use `rich.progress` alongside structlog.
The progress bar shows overall completion; structlog handles detailed event logging underneath.
These don't conflict — progress goes to stderr, logs go to stdout, or both go to their respective
handlers.

### Log Files

In development, write logs to both console and a rotating file in `logs/greenprint.log`.
Commit the `logs/` directory to `.gitignore` (already listed above). The file log is invaluable
when a run fails halfway through and you need to find where it went wrong without re-running
everything.

## Reference Data: Using `data-1-1.json`

Rather than generating reference data from a game dump, the provided `data-1-1.json` is the
source. Before Step 1 coding begins:

1. Inspect the structure of `data-1-1.json` to understand its schema
2. Write a one-time conversion script (`scripts/convert_reference_data.py`) that extracts the
   relevant recipe and entity fields into the `reference/recipes.json` and `reference/entities.json`
   formats defined in `CLAUDE.md`
3. Run the script once, commit the output files, then the script is no longer needed at runtime
4. The conversion script itself should be committed to `scripts/` for reproducibility — if the
   reference data ever needs to be regenerated, the script is there

This is cleaner than having the pipeline read `data-1-1.json` directly, because the reference
files are in a known, validated schema that the rest of the code depends on.
