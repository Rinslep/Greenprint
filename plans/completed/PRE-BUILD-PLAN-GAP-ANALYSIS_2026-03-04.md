# Greenprint — Gap Analysis & Implementation Plan

Generated by codebase audit against analytics targets. Last updated: 2026-03-04.

---

## Gap Analysis

---

### TARGET 1 — Production intent — PARTIAL

**Implemented:**
- `analysis/crafting_graph.py` builds a `nx.DiGraph` with all required graph-level attributes:
  `final_products`, `raw_inputs`, `intermediates`, `is_self_contained`, `has_cycle`, `byproduct_candidates`
- Orchestrator serialises and stores this as `summary["crafting_graph"]` in the `blueprints.summary` JSON column
- `GET /v1/blueprints/{id}/graph` reads and returns it

**Missing:**
- Blueprints are **not queryable by final product**. `parse_filter_string` in `api/dependencies.py`
  parses `final_product:electronic-circuit` correctly into a dict. But `storage.list_blueprints` only
  applies SQL `WHERE` clauses for `source_site` and `game_version`. A `final_product` key in the filter
  dict is silently ignored. The `is_self_contained` filter is likewise parsed but never applied.
- No SQL-level JSON path query for `summary->crafting_graph->final_products`. Both SQLite and PostgreSQL
  have JSON operators but neither is wired up.

---

### TARGET 2 — Machine ratios and efficiency — PARTIAL

**Implemented:**
- `analysis/ratio_analyser.py` computes `ideal_ratio`, `actual_ratio`, `efficiency` as `fractions.Fraction`
  for each supplier→consumer recipe pair, identified via the crafting graph's intermediate-item edges
- Beacon effects applied via `_compute_beacon_effects`; module effects via `_compute_module_effects`
- Bottleneck pair (lowest efficiency) identified and stored under `results["bottleneck"]`
- Fractions converted to float at storage boundary via `_serialise_summary` in the orchestrator

**Missing:**
- `analyse_ratios` receives a `nx.DiGraph` where edges connect *items* not recipes. The ratio logic
  traverses `G.predecessors(item_node)` / `G.successors(item_node)` to find item-mediated recipe pairs.
  This only finds pairs where the shared item is an intermediate. A recipe pair connected by a
  final-product output is skipped. This is a structural gap for blueprints without intermediates.
- No bottleneck expressed at the item level — only at the recipe-pair level.

---

### TARGET 3 — Throughput — PARTIAL

**Implemented:**
- `analysis/throughput_analyser.py` has all three layers: machine output rate (via `compute_machine_rate`),
  inserter delivery rate (`_get_inserter_rate`), belt lane capacity (via `belt_speed` on lane nodes)
- `lane_saturation` dict computed; `bottleneck_entity`, `bottleneck_type` set to minimum layer
- `actual_output_rate` accumulated per final product
- Stored and exposed via `/v1/blueprints/{id}/throughput`

**Missing:**
- Belt path walking loop does not correctly traverse splitters or underground exit nodes — these emit
  different outgoing node types and the traversal logic does not account for them.
- `bottleneck_type == "belt_lane"` incorrectly uses `entity.entity_number` (the machine's entity number)
  as `bottleneck_entity` — the belt lane node ID should be used instead.
- Filter inserter logic checks `filter_items` on inserter edges but belt lane nodes carry no item type
  annotations, so filtering on shared lanes can pass through the wrong items silently.
- `lane_saturation` keys serialise to strings like `"(3, 1, 'left')"` — valid JSON but unusual.

---

### TARGET 4 — Flags and data quality — PARTIAL

**Implemented:**
- `pipeline/broken_detector.py` implements all 6 required flags: `NO_POWER`, `POWER_GAP`,
  `FLOATING_INSERTER`, `BELT_DEAD_END`, `UNSUPPLIED_RECIPE`, `CONDITIONAL_BEHAVIOUR`
- `INFERRED_RECIPE` flag populated by `recipe_inference.py`, always added regardless of confidence
- `EARLY_VERSION` flag set by `version_filter.py`
- Modded blueprint rejection at decode time via `check_modded`
- All flags stored to `blueprints.flags` (JSON column)
- Flags surfaced in API response `warnings` array

**Missing:**
- `source_book_id` is never passed to `save_blueprint` in the orchestrator. The decoder sets
  `source_book_id` on child blueprint dicts as the raw string hash of the parent book, but this is a
  hash string — not a DB UUID. The orchestrator never maps this hash to a DB row ID. The
  `source_book_id` FK always stays `NULL`.
- `review_count` is set to 0 at the end of `_process_single` regardless of actual items added.
  `infer_recipes` adds items to the queue but the orchestrator never counts them.

---

### TARGET 5 — Basic motif extraction — PARTIAL

**Implemented:**
- `analysis/motif/lane_model.py` builds the full lane-level `nx.DiGraph` with per-lane nodes for
  belts/undergrounds/splitters, machine nodes, chest nodes, inserter edges
- `analysis/motif/extractor.py` performs BFS from machine output inserters, assigns categories,
  collects motif subgraphs with `source_machine` and `dest_machines` graph attributes
- `analysis/motif/canonicaliser.py` applies all 8 transformations (4 rotations × 2 mirrors), picks
  lexicographic minimum, MD5 hashes
- `storage.save_motif` correctly upserts with `occurrence_count` increment and recipe count merging

**Missing:**
- **Double extraction bug in orchestrator**: `extract_motifs(lane_graph)` is called twice — once in
  stage 9 (before `save_blueprint`, all results discarded) and again in stage 10 (used for DB save).
  The first call is entirely dead code.
- **Empty metadata on every stored motif**: the orchestrator always passes
  `source_recipes=None, dest_recipes=None, belt_type=None, uses_underground=False, uses_splitter=False,
  position_context=None` to `save_motif`. The motif subgraph carries `graph["source_machine"]` and
  `graph["dest_machines"]` with entity objects that have `.recipe` set, but none of this is read.
- `belt_type` is always `None` — derivable from the entity name stored on any `belt_lane` node within
  the motif.
- `uses_underground` and `uses_splitter` always `False` — derivable by checking edge types
  (`"underground"`, `"splitter"`) in the motif subgraph edges.

### TARGET 6 — Motif categories — PARTIAL (wrong taxonomy)

**Implemented (original taxonomy):**
- `_classify_motif` in `extractor.py` assigns: `DIRECT` (no belt nodes + inserter), `SPLIT` (splitter
  edge), `UNDERGROUND` (underground edge), `SIMPLE` (default)
- `MERGED` is in the spec but no logic assigns it — only single-output paths are traced

**Missing (revised taxonomy per analytics targets):**
- Analytics targets supersede the 5-category design with: primary category `DIRECT` vs `BELT`, plus
  structural flags `has_underground`, `has_splitter`, `is_sideloaded`, `is_multi_destination`
- `is_sideloaded`: no detection logic
- `is_multi_destination`: the extractor's `dest_machines` set already provides this — just needs a
  `len(dest_machines) > 1` check; not surfaced
- Neither `is_sideloaded` nor `is_multi_destination` exist as DB columns in `Motif`

---

- No concept of "family" in extractor, canonicaliser, or storage

## A — Prioritised implementation list

### Priority 1: things that block other things

**1. Fix motif metadata population in orchestrator** — `pipeline/orchestrator.py`

In the second motif extraction block (stage 10), after `canon_hash, canon_entities = canonicalise(motif_sg)`,
derive:
- `source_recipes`: from `motif_sg.graph["source_machine"]` → its entity's `.recipe` (count: 1)
- `dest_recipes`: from `motif_sg.graph["dest_machines"]` → each entity's `.recipe` (count: 1 each)
- `belt_type`: from `entity.name` on any `belt_lane` node in the motif
- `uses_underground`: `any(d.get("edge_type") == "underground" for _, _, d in motif_sg.edges(data=True))`
- `uses_splitter`: same pattern with `"splitter"`

This unblocks targets 5, 6, 12.

**2. Remove the dead first motif extraction pass** — `pipeline/orchestrator.py` lines 229–252

Delete the entire stage 9 block (`# Stage 9: Motif extraction (continue on failure)` before
`save_blueprint`). It runs `extract_motifs` and `canonicalise` then discards every result. The second
pass (stage 10) is the real one.

**3. Blueprint storage filter layer** — `storage/__init__.py`, `list_blueprints`

Add JSON path filter support for `final_product`, `is_self_contained`, `flag`. Use SQLite JSON functions
(`json_extract`, `json_each`) for dev; PostgreSQL JSONB operators work automatically. Start with:
- `flag`: `json_each(blueprints.flags)` + `value->>'$.flag' = ?`
- `final_product`: check membership in `json_extract(summary, '$.crafting_graph.final_products')`
- `is_self_contained`: `json_extract(summary, '$.crafting_graph.is_self_contained') = 1`

This unblocks target 11 and completes target 1.

**4. Apply per-route rate limiting** — all files under `api/v1/`

Add `from api.main import limiter` and `@limiter.limit(f"{settings.api_rate_limit_per_minute}/minute")`
to every route handler function. Without this the SlowAPI infrastructure is completely inert.
Closes target 14.

---

### Priority 2: partially done, close to complete

**5. Motif structural flags and revised taxonomy** — `pipeline/orchestrator.py`, `storage/models.py`

After populating `uses_underground` and `uses_splitter` (from priority 1 above):
- Add `is_multi_destination` boolean to `Motif` model: `len(motif_sg.graph["dest_machines"]) > 1`
- Add `is_sideloaded` boolean to `Motif` model: detect from inserter drop position relative to belt
  direction (near-lane but not terminal — currently no signal for this; requires extractor change)
- Revise `category` to `DIRECT` vs `BELT` as primary, store structural flags as separate columns
- Requires a DB schema migration for new columns

Closes target 6 and most of target 12.

**6. Motif storage filter layer for boolean columns** — `storage/__init__.py`, `list_motifs`

Add SQL WHERE clauses for `uses_underground`, `uses_splitter`, and new boolean columns once added.
Align filter key names (`has_underground` → `uses_underground` internally). Add ORDER BY support for
`occurrence_count`. Closes target 12.

**7. Implement Jaccard similarity in search endpoint** — `api/v1/analysis.py`, `search_similar`

After decode + validate, run `build_lane_model` → `extract_motifs` → `canonicalise` on the submitted
blueprint to get a set of canonical hashes. Then query `BlueprintMotif` joined to `Motif` to retrieve
motif hash sets for each stored blueprint. Compute `|A ∩ B| / |A ∪ B|` per stored blueprint. Apply
5-second timeout. Closes target 13.

**8. Fix `source_book_id` propagation** — `pipeline/orchestrator.py`

When `is_book` is true, the decoder sets `source_book_id` on child dicts as the book's raw hash string.
Pass this value through to `save_blueprint` as `source_book_id`. (SQLite won't enforce the FK strictly
against a non-UUID hash string; fix FK mapping properly before PostgreSQL deployment.)

**9. Fix `review_count` tracking** — `pipeline/orchestrator.py`

`result.review_queue_items = review_count` always assigns 0. Have `infer_recipes` return a count of
items added to the review queue, or query `pipeline/review_queue.py` after the call.

---

### Priority 3: missing entirely (implement in this order)

**10. Run-length normalisation + family hash** — new file `analysis/motif/family_hash.py`

Build an abstract graph from a motif subgraph where consecutive same-tier, same-direction belt nodes
are collapsed into a single abstract edge with a `length` attribute. Hash with:
- Belt tier normalised to `"belt"` (ignoring yellow/red/blue)
- Inserter type normalised to `"inserter"`
- Run lengths preserved as abstract edge attributes

Store as `family_hash TEXT` column on `Motif`. Add `family_occurrence_count INT` column. Requires
schema migration. Closes targets 7 and 9.

**11. Sub-motif hierarchy** — extend `analysis/motif/family_hash.py`

After computing the family hash for a motif, generate simplified variants by stripping one structural
feature at a time (underground pair → plain belt run; splitter → single pass-through; sideload →
direct drop). Look up each variant's family hash in the DB. Set:
- `elaboration_depth INT` = count of features stripped to reach simplest ancestor
- `sub_motif_of_family TEXT` = family hash of the simplest found ancestor

Requires new columns + schema migration. Closes target 8.

**12. Tileability detection** — new file `analysis/motif/tileability.py`

After all motifs are extracted per blueprint, group by canonical hash and compute spatial offset vectors
`(dx, dy)` between occurrences of the same motif. If any offset appears ≥ threshold times, record as
tileable with that vector. Aggregate across blueprints to set `is_tileable` on `Motif` when the pattern
tiles regularly. Requires `is_tileable BOOL`, `tile_vector JSON`, `tile_count INT` columns on `Motif`
plus a schema migration. Closes target 10.

## B — Motif pipeline trace and shortfalls

Trace from raw blueprint string to stored motif with all fields populated:

**Step 1: `decode(raw)` ✓**
Works correctly. Books dissolved, child blueprints carry `source_book_id` (raw hash, not DB UUID).

**Step 2: `validate(decoded)` ✓**
Pydantic schema + 3 semantic checks. Works correctly.

**Step 3: Version/modded checks ✓**
Works correctly. Modded entities/recipes rejected; EARLY_VERSION flagged.

**Step 4: `build_lane_model(wrapper)` → `lane_graph` — mostly correct**
Belts, undergrounds, splitters, inserters, machines, chests all modelled. Known gap: sideloading is
partially modelled (near-lane targeting) but the extractor has no `is_sideloaded` signal. Underground
exit nodes emit a `belt_flow` edge to an adjacent position that may not be a registered belt entity,
creating dangling edge targets.

**Step 5: Stage 9 — first `extract_motifs` call — DEAD CODE**
BFS runs. Motifs built. `canonicalise` runs. Metadata dict created with all-default/empty values.
No `bp.id` exists yet so nothing is saved. All results discarded. `except Exception: pass` silently
swallows errors. **Delete this block.**

**Step 6: `save_blueprint(session, ...)` ✓**
Blueprint written to DB with flags and summary. `source_book_id` always `NULL` (propagation bug).

**Step 7: Stage 10 — second `extract_motifs` call — runs but with empty metadata**

For each motif subgraph:
- `canonicalise(motif_sg)` → `(canon_hash, canon_entities)` ✓
- `category` derived from `motif_sg.graph.get("category", "SIMPLE")` ✓
- `source_recipes`: always `None` — extractor has `graph["source_machine"]`; entity has `.recipe`; **not read**
- `dest_recipes`: always `None` — extractor has `graph["dest_machines"]`; entities have `.recipe`; **not read**
- `belt_type`: always `None` — lane nodes carry `entity.name`; **not read**
- `uses_underground`: always `False` — edge type `"underground"` not checked
- `uses_splitter`: always `False` — edge type `"splitter"` not checked
- `position_context`: always `None` — no concept defined anywhere
- `save_motif` upsert: `occurrence_count` increments correctly ✓; recipe merging does nothing (both dicts `None`)

**Summary of motif pipeline failures in order of impact:**

1. Dead double-extraction wastes CPU on every blueprint
2. `source_recipes` and `dest_recipes` always null — catalogue unusable for recipe-based queries
3. `belt_type`, `uses_underground`, `uses_splitter` always null/false — structural queries return wrong results
4. No `family_hash` — tier-normalised grouping impossible
5. No `elaboration_depth` — structural hierarchy absent
6. No tileability — pattern frequency analysis absent
7. `MERGED` category never assigned — multi-input merging patterns go undetected
8. `is_sideloaded`, `is_multi_destination` not tracked anywhere
