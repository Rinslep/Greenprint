## Action 1 — Factorio Prints and Factorio School Are the Same Database

PLAN.md lists `factorio_prints.py` and `factorio_school.py` as separate scrapers with different
approaches ("HTTP pagination" and "HTTP + BeautifulSoup" respectively). This is wrong.

From prior research: **factorioprints.com and factorio.school share a single Firebase Realtime
Database backend.** They are the same data. Scraping both would produce 100% duplicates.

**Correct approach:**

Write a single `scraper/factorio_prints.py` that is a Firebase REST client, not an HTML scraper.
The backend is the Firebase project `facorio-blueprints` (note the typo — one 't').

The two relevant endpoints are:
```
GET https://facorio-blueprints-default-rtdb.firebaseio.com/blueprintSummaries.json
    ?orderBy="$key"&limitToFirst=1000&startAt="{last_key}"

GET https://facorio-blueprints-default-rtdb.firebaseio.com/blueprints/{id}.json
```

Algorithm:
1. Paginate through `/blueprintSummaries` using `orderBy + limitToFirst + startAt`
2. For each summary ID, fetch `/blueprints/{id}.json` for the full record
3. Extract the blueprint string from the `blueprintString` field
4. Store the Firebase key as `source_id` in the progress tracker for resumability

Delete the `scraper/factorio_school.py` stub entirely — it should not exist.

**Be polite:** Firebase is a paid service for the site owner. Use a 0.5–1s delay between requests.

## Clarification 4 — UUID Generation Must Be Explicit

PLAN.md specifies `String(36)` for PKs but does not say where UUIDs are generated.

Generate UUIDs in Python, not the database, using `uuid.uuid4()`. This ensures portability
between SQLite (which has no native UUID type) and PostgreSQL.

Set the default at the model level:
```python
import uuid
id: Mapped[str] = mapped_column(String(36), primary_key=True, default=lambda: str(uuid.uuid4()))
```

This must be consistent across all four models. Do not rely on the database to generate IDs.

## Clarification 5 — Fraction Serialisation Into the Summary JSON

The ratio and throughput analysers store results as `fractions.Fraction` internally. The
`summary` column in the Blueprint model is JSON, which cannot store Fraction objects.

The plan mentions `_fraction_to_float()` in the orchestrator but does not define its scope.

Define a single `_serialise_summary(summary: dict) -> dict` function in the orchestrator that
recursively converts any `Fraction` value to a `float` before storage. This must handle:
- Top-level Fraction values
- Fraction values nested inside dicts
- Fraction values inside lists

Do not convert Fractions to floats inside the analysis modules themselves — keep them exact
internally and only convert at the storage boundary in the orchestrator.

## Clarification 6 — Pipeline Error Handling Per Stage

PLAN.md defines the orchestrator pipeline as a sequence of stages but does not specify what
happens when a stage fails partway through.

Use a per-stage catch pattern: if a non-critical stage fails, log the error, attach a flag,
and continue with subsequent stages. Only abort the entire pipeline for unrecoverable failures.

| Stage | Failure behaviour |
|---|---|
| `decode()` | Abort — nothing to work with |
| `validate()` | Abort — corrupted data |
| `check_version()` / `check_modded()` | Abort — explicitly out of scope |
| `detect_broken()` | Continue — attach flags, proceed |
| `infer_recipes()` | Continue — attach flags, queue items, proceed |
| `build_crafting_graph()` | Continue — log warning, store empty graph |
| `analyse_ratios()` | Continue — log warning, store empty ratios |
| `build_lane_model()` | Continue — log warning, skip throughput |
| `analyse_throughput()` | Continue — log warning, store empty throughput |
| `extract_motifs()` / `canonicalise()` | Continue — log warning, no motifs stored |
| `save_blueprint()` | Abort — if we can't save, the whole run is wasted |

Log every stage failure with the blueprint hash and source URL so failures can be reproduced.
Never silently swallow exceptions — every caught exception must produce a log entry.

## Clarification 7 — Define `PipelineResult` Before Writing the Orchestrator

PLAN.md references `PipelineResult` as the return type of `process_string()` but does not
define it. Define this dataclass in `pipeline/orchestrator.py` before implementing the function:

```python
@dataclass
class PipelineResult:
    success: bool
    blueprint_ids: list[str]      # IDs of saved blueprints (may be >1 for books)
    rejected: bool                 # True if rejected at decode/version/mod stage
    rejection_reason: str | None
    flags: list[dict]              # Aggregate of all flags across all stages
    review_queue_items: int        # Count of items added to the review queue
    errors: list[str]              # Non-fatal stage errors encountered
```

The orchestrator tests should assert on `PipelineResult` fields, not on side effects alone.

## Clarification 8 — Author Anonymisation Is the Single Chokepoint

The plan correctly places author anonymisation inside `save_blueprint()`. This is the right
pattern — one place where `author_raw` (a username string) is converted to `author_hash`
(a SHA-256 hex digest) before anything touches the database.

Enforce this by:
1. The `author_raw` parameter must never be logged by the orchestrator or any scraper
2. The `Blueprint` model must not have an `author_raw` column — only `author_hash`
3. The Pydantic response schemas in `api/v1/schemas.py` must not include `author_hash`
   in any response model — it is stored but never exposed via the API

Add a test: `test_author_never_in_api_response` — POST a blueprint with a known author,
GET it back, assert the response contains neither the raw username nor the hash.

## Clarification 9 — Similarity Search Is Synchronous and Slow

The `/v1/analysis/search` endpoint decodes a submitted blueprint string on-the-fly and finds
similar blueprints via Jaccard similarity on motif hashes. This runs the full decode →
validate → lane model → motif extraction pipeline on the submitted string.

For large blueprints (2000+ entities) this could take several seconds. Do not make this
endpoint async in a way that implies it is fast. Instead:

1. Add a hard entity count limit — reject blueprints with more than 500 entities for the
   search endpoint, returning a `422` with a clear message
2. Add a timeout (5 seconds) — if the pipeline takes longer, return `408`
3. Document both limits in the response schema

This can be relaxed later with a proper task queue. For now, keep it simple and safe.
