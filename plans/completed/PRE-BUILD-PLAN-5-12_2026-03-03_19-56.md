## Clarification 4 — Lane Side Determination

This is the most subtle logic in the entire lane model. Implement and test this before anything
else in Step 10.

**The rule:** Left and right lanes are defined relative to the belt's direction of travel,
not absolute screen coordinates. An inserter targets the **near lane** — the lane on the
same side of the belt tile as the inserter's position.

**Lane orientation by belt direction:**

| Belt direction | Left lane side | Right lane side |
|---|---|---|
| North (0) | West side of tile | East side of tile |
| East (2) | North side of tile | South side of tile |
| South (4) | East side of tile | West side of tile |
| West (6) | South side of tile | North side of tile |

**Algorithm for `_determine_lane_side(inserter_pos, belt_tile_pos, belt_direction)`:**

1. Compute the vector from belt tile centre to inserter position: `(dx, dy)`
2. Based on belt direction, determine which axis is the "side" axis:
   - North/South belts: side axis is X (positive X = East = right for North, left for South)
   - East/West belts: side axis is Y (positive Y = South = right for East, left for West)
3. The sign of the side-axis component determines left vs right

Write `test_lane_side_all_orientations` before implementing the function. This test must
cover all 4 belt directions with an inserter on each side (8 cases total). A wrong
implementation here silently corrupts throughput analysis and motif extraction.

## Clarification 5 — Underground Belt Matching: Nearest Exit Wins

PLAN.md says to match underground pairs by same tier, same direction, within max distance.
This is incomplete. Factorio's actual rule is:

**The nearest valid exit claims the nearest entrance.** If there are multiple exits in range,
the first one encountered (shortest distance) is the match. Chained underground segments work
because each exit-entrance pair is matched in distance order.

Implement underground matching as follows:
1. Separate all underground belt entities into `inputs` and `outputs` by their `type` field
2. For each `input` entrance, collect all candidate `output` exits of the same tier and
   direction within `underground_max_distance` tiles
3. Sort candidates by distance ascending
4. Match the nearest candidate exit that has not already been claimed by a closer entrance
5. Add a single logical edge for each matched pair
6. Unmatched entrances or exits are flagged as potential broken blueprint indicators

Write `test_underground_chained_nearest_wins` to verify that when two exits are in range of
one entrance, the nearer one is matched.

## Clarification 6 — Splitter Footprint Is Direction-Dependent

PLAN.md describes splitters as "2×1 footprint" but does not specify orientation handling.

A splitter's footprint depends on its direction:
- Facing **North (0) or South (4)**: 2 tiles wide (X), 1 tile tall (Y)
- Facing **East (2) or West (6)**: 1 tile wide (X), 2 tiles tall (Y)

The position stored in the blueprint is the **centre** of the splitter. For the spatial
position index, both tiles must be registered:

```python
def _get_splitter_tiles(entity) -> list[tuple[int, int]]:
    cx, cy = round(entity.position.x), round(entity.position.y)
    if entity.direction in (0, 4):  # N or S — wide axis is X
        return [(cx - 1, cy), (cx + 1, cy)]  # or (cx, cy-0.5) — verify against game data
    else:  # E or W — wide axis is Y
        return [(cx, cy - 1), (cx, cy + 1)]
```

Verify the exact tile positions against a real splitter blueprint before implementing. A
splitter placed incorrectly in the spatial index will cause lane model edge construction to
fail silently.

Add `test_splitter_footprint_north` and `test_splitter_footprint_east` to the lane model tests.

## Clarification 7 — Byproducts in Crafting Graph Final Products

The crafting graph definition of `final_products` — items produced but not consumed internally
— is correct but has an edge case with multi-output recipes (oil refining, coal liquefaction,
uranium processing).

If a blueprint processes one output of a multi-product recipe but not the others, the unused
outputs will appear as `final_products` even though they are genuinely unused byproducts.

Add a `byproduct_candidates` field to the crafting graph attributes:
```python
# Items that are outputs of multi-product recipes AND not consumed internally
# These may be final products OR unused byproducts — flag for human review
graph.graph["byproduct_candidates"] = [...]
```

The logic:
1. For each recipe with more than one output item, collect all output item names
2. If any of those items are in `final_products` and the recipe has 2+ outputs, add them to
   `byproduct_candidates`

This does not change `final_products` — it adds a parallel list for transparency.

## Clarification 8 — Recipe Inference Expected Hit Rate

The inference logic depends on inserters having their `filters` field set. In practice, most
inserters in real Factorio blueprints have **no filter set** — players don't configure them
because machines self-sort. This means the majority of machines with no recipe will have
no item hints available and will go directly to the review queue rather than being inferred.

This is correct behaviour — do not attempt to compensate by making inference more aggressive.
The spec says "infer from context if possible, otherwise queue." "Context unavailable" is a
valid outcome that should be logged clearly:

```
INFO  blueprint {id}: recipe inference — 0 hints available for machine {n}, adding to queue
```

Do not treat a low inference rate as a bug.
